# 需求定义：Echo of Photons

## 文档目的

本文档用于明确 Echo of Photons 当前阶段的产品定位、目标用户、核心需求、边界和后续演进方向，作为 `tech-spec.md` 与 `dev-plan.md` 的直接依据。

---

## 1. 项目名称与定位【A】

### 1.1 项目名称

Echo of Photons

### 1.2 一句话定位

一款以手机为观天窗口，帮助用户在真实天空中找到目标、判断是否值得观测，并逐步建立观测能力的产品。

### 1.3 定位补充

本产品不是静态天文百科，也不是只会解释的星图页面。它的第一核心是让用户在真实天空里完成“找得到、对得上、看得懂”。

产品整体结构分为四层：

1. 首页：今晚行动入口
2. 2D 星图模式：平面参考图
3. 观察模式：真实天空窗口
4. 工具页：观测条件与计划工具

产品主次关系明确为：

- 入口层：先带用户开始观星
- 成长层：再支持持续的观测判断与计划

也就是：`前者做入口，后者做成长`。

---

## 2. 目标用户【A】

### 2.1 第一批目标用户

对星空和宇宙有兴趣，但尚未形成稳定观测习惯的普通用户。

### 2.2 用户特征

- 对亮星、行星、星座、流星雨这类高认知天象有天然兴趣
- 愿意拿起手机去看天，但不愿先学一堆专业参数
- 在真实夜空里经常遇到“看见了但不知道是什么”的问题
- 对工具有期待，希望它能帮助做决定，而不是只讲故事

### 2.3 当前主要问题

- 不知道今晚先看什么
- 不知道当前位置是否适合观测
- 对着天空时，难以把手机画面和真实天空对应起来
- 即使知道对象名字，也不清楚现在是否适合看、多久后更适合看
- 缺少从一次性尝试走向持续观测的产品路径

## 3. 核心业务需求【A】

### 3.1 MVP 需求总表

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| R-001 | 首页行动入口 | P0 | 用户打开后应立即知道今晚先做什么 |
| R-002 | 2D 星图参考模式 | P0 | 提供稳定的平面星图，用于查位置与看结构 |
| R-003 | 观察模式 | P0 | 以手机朝向作为视窗，建立真实天空窗口体验 |
| R-004 | 目标确认与详情承接 | P0 | 用户找到对象后，先确认，再决定是否进入详情页 |
| R-005 | 工具页观测条件判断 | P1 | 帮用户判断今晚值不值得看、哪里更适合看 |
| R-006 | 未来天象日历 | P1 | 支持未来一年流星雨等事件的计划型浏览 |
| R-007 | 观测参考图 | P1 | 用肉眼参考图和摄影参考图增强理解与可信度 |
| R-008 | 后端数据能力扩展 | P1 | 为天象事件、区域比较、参考图内容提供稳定数据层 |

### 3.2 首页行动入口

首页是找星入口页，不是内容堆叠页。

首页第一版动作结构固定为：

1. `开始看一下`
2. `看 2D 星图`
3. `查看观测条件`
4. `换一个目标`

权重关系为：

- 最强：`开始看一下`
- 第二层：`看 2D 星图`、`查看观测条件`
- 最轻：`换一个目标`

首页应提供的轻信息：

- 今晚观测条件
- 最佳观察时间
- 附近更优区域提示（仅在有明显差异时出现）

首页与观察模式的关系：

- 首页负责告诉用户“今晚先看什么”
- 观察模式负责让用户真正抬头去找

### 3.3 2D 星图参考模式

2D 星图模式保留为稳定参考图，不承担真实朝向窗口体验。

它的职责是：

- 看整体分布
- 查目标大致位置
- 看星座和亮星的平面结构
- 承接搜索与目标跳转

它不是观察模式的替代品，也不承载沉浸式观测感。

### 3.4 观察模式

观察模式是产品核心体验。

#### 核心原则

- 天空坐标固定
- 手机朝向改变的是视窗，不是整张星图被拖动
- 屏幕中心代表当前正对着的天空区域
- 用户得到的是“站在地球上抬头看天”的感觉，而不是旋转一张 2D 图

#### 准确度目标

第一版追求的是 `区域可信级`：

- 亮星、亮行星、大方向基本对得上
- 用户能在合理区域找到目标
- 能通过现实亮目标与屏幕中对应亮目标建立信任

#### 入口规则

观察模式默认进入 `当前天空`，但带着首页推荐目标的轻线索进入。

含义是：

- 不强行把视野跳到某个对象
- 先尊重此时此地的真实天空
- 同时给用户一个很轻的“今晚可以先找它”的任务感

#### 目标引导

目标引导强度确定为 `轻引导`：

- 未接近时：只保留轻任务存在感
- 接近目标区域时：逐渐增强确认辅助
- 接近确认时：名称更明显、命中更容易

不做：

- 大箭头
- 持续闪烁框
- 过多方向口令式提示

#### 点击与命中

移动端点击问题的解决原则是：

- 目标接近确认状态时，点击热区动态增大
- 不靠堆更多文案解决，而靠更容易命中解决

#### 中等聚焦态

点击对象后不直接跳详情页，而进入 `观察确认层`。

结构固定为：

1. 目标名
2. 一句短状态（位置 + 观测判断）
3. `查看详情`
4. `缩回天空`

第一版采用 `轻收焦`，不做强缩放、不做大面板。

#### 时间滑动

时间滑动属于观察模式，不属于 2D 星图模式。

规则为：

- 默认半隐藏
- 初次进入时轻露出一次，提示其存在
- 用户可通过轻按钮或手势呼出
- 第一版只看 `今晚时间线`

时间滑动表达方式确定为：`真实模拟为主，产品辅助为辅`。

具体表现为：

- 天空背景亮度变化
- 星体可见性变化
- 目标状态变化
- 星座结构在更适合的时机更容易识别
- 最佳观察时间在时间线里被轻强调

#### 星座结构

星座不是静态重线条覆盖层。

观察模式中采用：

1. 关键亮星先变明显
2. 结构感再逐步增强
3. 若用户开启辅助，再出现较弱连线

用户拥有开关权，但入口应藏在轻菜单里，不占主舞台。

### 3.5 工具页

工具页不是首页复读机，也不是偏叙述的说明页。它应成为真实的观测决策工具页。

第一版主模块确定为：

1. 今晚观测总结论
2. 影响因素
3. 附近更优区域提示
4. 近期可关注天象

#### 今晚观测总结论

至少回答：

- 今晚整体是否适合看
- 当前定位在哪里
- 最佳开始时间
- 一句短结论

#### 影响因素

第一版优先展示：

- 云量
- 月光干扰
- 天空清晰度 / 通透感
- 观测窗口

#### 附近更优区域提示

产品口径固定为：

从用户当前位置出发，按近到远比较周边区域的天气观测条件，返回最近的显著更优区域；若无显著差异，则明确提示附近整体条件接近。

规则：

- 从近到远逐圈排查
- 先找最近的明显更优区域
- 第一版主要看天气条件，不先做重光害系统
- 结果只给一个最近最优区域，不给排行榜

返回信息建议为：

- 区域名
- 比当前位置好在哪里
- 大致距离 / 相对方向
- 一句行动建议

#### 近期可关注天象

这是工具页内的轻预告模块，不是完整事件页。

没有内容时不显示。

### 3.6 未来天象日历

未来天象日历独立成页，工具页内只放轻入口。

#### 第一版范围

- 时间范围：未来一年
- 第一类内容：流星雨预测
- 覆盖口径：`未来一年内中国境内有观测意义的流星雨`

#### 表达方式

- 计划型为主
- 百科型为辅

#### 每条流星雨字段

1. 流星雨名称
2. 活跃期
3. 峰值夜晚
4. 预估强度
5. 中国境内推荐观测时段
6. 观测提醒
7. 理想观测地类型
8. 中国境内更优区域建议

#### 地点粒度

- 第一版：区域级建议
- 后续：城市周边级

#### 页面结构

- 全年时间轴
- 按月展开的事件列表

### 3.7 观测参考图

摄影师星空照片的第一定位是 `观测参考图`，不是首页氛围素材。

默认采用两层结构：

1. 肉眼参考
2. 摄影参考

但默认先给肉眼参考，帮助用户理解“我现在真实大概能看到什么”；摄影参考用于补充“理想条件下可能看到什么”。

最适合接入的页面：

- 详情页
- 未来天象日历 / 事件页

不优先放入首页主链路。

### 3.8 核心用户路径

#### 主路径一：今晚抬头找星

首页 → 开始看一下 → 观察模式 → 轻引导找目标 → 中等聚焦态 → 详情页（可选）→ 缩回天空继续看

#### 主路径二：今晚条件判断与换地点决策

首页 → 查看观测条件 → 工具页 → 今晚观测总结论 → 影响因素 → 附近更优区域提示 → 决定是否换地方 → 再进入观察模式

#### 主路径三：未来计划型使用

首页 / 工具页 → 近期天象预告 → 未来天象日历 → 查看全年流星雨 → 看峰值时间与区域建议 → 形成未来观测计划

## 4. 非功能需求【B】

### 4.1 平台

当前产品主体是移动端优先的 Web 应用。

要求：

- 主要交互优先适配手机端
- 桌面端保留参考访问能力
- 观察模式优先服务移动端

### 4.2 性能与流畅度

- 首页第一屏应快速可用
- 2D 星图与观察模式的基础交互需保持流畅
- 搜索、目标跳转、详情承接不能有明显卡顿
- API 响应应稳定，避免随机失败造成“加载失败”体验

### 4.3 稳定性

- 无定位权限时产品仍可工作
- 观察模式权限失败时必须有平滑回退
- 搜索命中失败时必须有明确反馈
- 目标详情失败时必须有兜底表现

### 4.4 安全与隐私

- 位置、方向等权限必须按需请求
- 不在前端保存真实密钥
- 数据库连接串只存在服务端环境变量中

## 5. 代码风格与架构模式【B】

### 5.1 总体原则

- 先把主体验做对，再补重功能
- 以页面职责为边界，不把所有能力混成一个超级页面
- 以现有 Next.js + TypeScript + PostgreSQL 技术主线继续演进
- 只在需要时增加抽象，不为未来假设提前设计重系统

### 5.2 前后端职责

- 前端负责页面、交互、视图状态与产品承接
- 后端负责推荐、对象详情、观测摘要、事件数据、区域比较等数据能力
- 数据库负责对象、卡片、事件、区域结果、观测参考图等结构化内容

### 5.3 后端当前与后续定位

当前后端属于：`内容型 + 计算型轻后端`

后续优先演进方向：

1. 天象与观测条件数据层
2. 观测参考内容层
3. 个人观测计划层

## 6. 约束条件与边界场景【B】

### 6.1 当前明确不做

| 编号 | 不做项 | 原因 |
|---|---|---|
| N-001 | 重社交与社区 | 偏离当前主价值 |
| N-002 | 排行榜与打卡体系 | 不解决当前核心问题 |
| N-003 | 一开始就做重后台权限系统 | 与当前产品阶段不匹配 |
| N-004 | 一上来做全国具体观星地排行榜 | 数据维护重，且容易失真 |
| N-005 | 观察模式中的强导航 UI | 会破坏真实看天感 |
| N-006 | 把首页做成工具页或内容页 | 会削弱主入口作用 |

### 6.2 第一版边界

- 2D 星图模式与观察模式分工明确，不混做一个模式
- 观察模式追求区域可信级，不追天文台级精度
- 流星雨第一版只做未来一年总览，不做全量天象百科
- 更优区域提示第一版先做区域级，不先做景点级
- 观测参考图先做参考，不先做作品社区

---

## 7. 当前结论与下一步【A/B】

### 7.1 当前结论

Echo of Photons 当前已明确为：

- 首页驱动的观星入口产品
- 观察模式是核心体验
- 2D 星图模式是参考模式
- 工具页是观测判断工具页
- 天象日历承担长期计划价值
- 参考图承担可信度与预期管理价值
- 产品主线是：先帮用户开始观星，再逐步支持持续决策

### 7.2 下一步建议

在本需求文档基础上，下一步技术与开发规划应重点回答：

- 观察模式如何稳定落地为真实天空窗口
- 工具页的数据能力如何从轻摘要扩展到区域比较与事件表
- 后端如何从轻接口层演进到事件数据层、内容层与个人计划层
- 开发阶段如何按主路径优先级推进，而不是零散叠功能
