## D-038 为什么详情页必须把用户送回探索，而不是停在内容页？

### 问题

当天体详情页出现后，它应该成为一个独立内容终点，还是应该承担“解释之后再把用户送回夜空继续探索”的职责？

### 背景

在当前产品路径里，用户往往先被首页推荐激发，再进入星图识别，再通过对象点击进入详情。如果详情页只是静态解释页，整个体验会在最关键的“刚刚产生兴趣”的节点断掉。

### 用户声音

- “我觉得这一步也要有 但是我觉得也要有回来的方法 让用户继续回来沉浸式探索”
- “OK”

### AI 判断

详情页不应作为终点页，而应是“解释 + 再送回探索”的中继页：

- 详情页负责解释对象是什么、为什么值得看
- 但主动作不应只停留在内容消费
- 它应该明确鼓励用户回到星图继续找、继续看、继续点
- 如果技术上可行，返回时最好恢复最近一次星图上下文，而不是把用户丢回默认状态

### 影响范围

- 影响详情页主按钮文案与动作优先级
- 影响首页 -> 星图 -> 详情 -> 星图 的闭环是否顺畅
- 影响 design-spec 中详情页是否被定义为终点内容页

### 最终结论

已拍板：

详情页不是终点内容页，而是解释后的承接页。主动作应引导用户继续回到夜空探索，且回流体验尽量保持最近一次星图上下文。

### 复盘 / 学习点

当产品目标不是“读完信息”，而是“被继续带去探索”时，详情页的职责就不能只看内容完整性，还要看它有没有把探索势能接住。

## D-039 为什么首页第一屏推荐区采用“一主一辅 + 条件层”的结构？

### 问题

首页第一屏到底应该把推荐做成多个并列卡片、天气模块 + 推荐模块，还是收敛成一个主推荐、一个辅推荐和一层条件说明的结构？

### 背景

首页承担的是“今天打开后我先做什么”的入口职责。如果第一屏信息太散，用户会在推荐、天气、解释、工具之间来回分心；如果只给一个死板目标，又会缺少灵活感。

### 用户声音

- “那肯定是推荐区最大”
- “我倾向于同主题补充”
- “这三个 我觉得都是对观测条件的 影响最大的依据 就这三个”
- “我觉的是B”

### AI 判断

首页第一屏最适合收敛为“一主一辅 + 条件层”的结构：

- 主推荐负责给出今晚最值得先开始的目标和理由
- 辅推荐不再做第二个独立大块，而是作为同主题补充，给用户一个更轻的抓手
- 条件层不独立成长为天气面板，只服务于推荐可信度与行动感
- 条件层再拆成依据层与行动层，一个负责客观条件，一个负责把条件翻译成“今晚怎么开始更合适”

### 影响范围

- 影响首页第一屏信息架构
- 影响推荐模块与天气/观测条件模块的边界
- 影响主动作、次动作和辅推荐是否会互相打架

### 最终结论

已拍板：

首页第一屏采用“主推荐 + 条件层 + 辅推荐”的结构。主推荐最大，辅推荐保持同主题轻入口，条件层只承接推荐依据与行动建议，不发展成独立天气面板。

### 复盘 / 学习点

一个好的首页入口不是信息越多越好，而是让用户在最短时间里同时获得“我先做什么”和“为什么现在值得做”的信心。

## D-040 为什么首页主推荐卡采用轻星空风格，而不是重沉浸式海报卡？

### 问题

首页主推荐卡的视觉表达，到底应该做成明显的沉浸式星空海报，还是只保留轻星空气质？

### 背景

产品整体气质需要和夜空、宇宙、探索感发生联系，但首页本身承担的是“激发 -> 送入星图”的职责，不是替代星图页完成沉浸式体验。

### 用户声音

- “其实我觉得沉浸式是要有的”
- “但是只是风格接近这种星空的感觉 但不用太沉浸式”
- “非常轻得到动态”

### AI 判断

首页主推荐卡最适合采用轻星空风格探索卡：

- 允许深夜底色、暖高光、微光与稀疏星点
- 允许极轻动态，例如慢呼吸、弱闪烁
- 但不能做成重海报、重场景、重颗粒的沉浸式视觉
- 因为首页的职责是邀请进入夜空，不是把夜空本体体验提前消耗掉

### 影响范围

- 影响首页主推荐卡的背景、装饰、动效强度
- 影响首页与星图页之间的职责区分
- 影响产品整体气质是否既有宇宙感又不失信息清晰度

### 最终结论

已拍板：

首页主推荐卡采用轻星空风格探索卡。允许轻微星光装饰与极轻动态，但不做重沉浸式海报卡，完整抬头感与夜空本体体验交给星图页承担。

### 复盘 / 学习点

沉浸感不是每一页都要平均分配的。成熟体验会把最强的场景感留给最该承担它的页面，而不是在入口处一次性用完。

## D-041 为什么第一轮星图候选方案只看 2-3 个，并优先看商业 SDK / 组件？

### 问题

第一轮星图候选方案，应该广撒网看很多工具，还是只控制在极少数候选里快速试选？候选来源又该优先看商业 SDK、开源库，还是现成网页产品？

### 背景

星图是本项目主体验的底层承载，但第一阶段的真正目标不是做星图选型研究项目，而是尽快判断哪类底层能力能承接首页 -> 星图 -> 详情这条产品闭环。

### 用户声音

- “商业sdk和开源web星图库的区别在哪”
- “OK”
- “可以”

### AI 判断

第一轮候选方案应控制在 2-3 个以内，并优先看商业 SDK / 组件：

- 商业 SDK / 组件通常在接入文档、事件能力、对象点击承接、时间地点控制上更成熟
- 第一轮更重要的是快速验证“能不能接住主路径”，而不是先追求完全控制权
- 开源 Web 星图库适合作为对照组，帮助判断商业方案是否真的值得付出成本
- 完整产品型网页星图暂不优先，因为它们更容易把产品带回“借别人的完整体验”，而不是接入我们自己的产品流程

### 影响范围

- 影响第一轮技术调研范围与节奏
- 影响后续 PoC 时间是否可控
- 影响项目是否会在星图底层选型阶段消耗过多精力

### 最终结论

已拍板：

第一轮星图候选方案控制在 2-3 个以内，优先看商业 SDK / 组件，其次看开源 Web 星图库，暂不优先看完整产品型网页星图。

### 复盘 / 学习点

技术调研不是候选越多越认真，而是越早建立清晰筛选顺序，越能把精力留给真正要被验证的产品闭环。
