# 开发计划：Echo of Photons

## 文档目的

本文件用于定义 Echo of Photons 第一阶段 MVP 的开发计划。
它的目标不是描述整个长期项目路线，而是把当前已经确认的产品与技术决策，转化为可执行的第一版交付顺序。

本计划只覆盖第一阶段 MVP。
后续版本应在现有项目骨架之上继续增量迭代，而不是重复基础环境搭建，除非技术路线被推翻，或产品形态发生根本变化。

---

## 阶段 1：项目骨架与基础环境

### 目标

建立第一阶段可运行的工程骨架，包括前端路由、后端入口结构和数据库连接基础。

### 任务清单

- 初始化 Next.js 项目
- 建立基础目录结构：`app / features / server / data-access / components / lib`
- 搭建全局布局外壳
- 确立统一 API 返回结构
- 准备 PostgreSQL 基础连接
- 准备环境变量加载与 DB Client

### 验证标准

- 项目可以成功启动
- 首页、星图页、详情页、工具页的空路由可以访问
- 至少一个测试 API 路由返回统一结构
- 数据库连接可以成功验证

---

## 阶段 2：星图候选 PoC 与方案选择

### 目标

用轻量真实外壳验证第一轮星图候选方案，并锁定第一阶段要采用的星图能力。

### 第一轮候选顺序

1. `Aladin Lite`
2. `Stellarium Web / Web Engine`
3. `WorldWide Telescope Web Control`

### 任务清单

- 搭建一个轻量星图 PoC 外壳，而不是裸技术 demo
- 保持很轻的顶部区域、一个主星图区、一个轻底部承接区，以及约 3 个轻工具占位
- 验证固定时间与地点切换行为
- 验证对象点击行为，并查看返回的对象信息
- 验证对象名称是否能顺利进入本地 resolve 流程
- 验证默认 UI 是否能收进我们的产品方向
- 为每个候选记录一份 PoC 结论

### 一票否决项

候选方案只要出现以下任一情况，立即淘汰：

1. 不能嵌入到 Web 页面结构中
2. 不能按时间与地点控制天空变化
3. 点击对象后拿不到稳定对象名称

### 评分维度

对通过一票否决层的候选，按以下维度评分：

1. Web 接入难度
2. 时间与地点控制质量
3. 对象点击事件质量
4. 返回对象信息质量
5. UI 可裁剪程度
6. 新手认星友好度
7. 对首页 -> 星图 -> 详情闭环的支持程度

### 分数含义

- `0`：不支持或明显不适合
- `1`：勉强可用，但风险很高
- `2`：基本可用
- `3`：非常适合第一版

### 验证标准

- 三个候选方案都有可比较的 PoC 记录
- 至少一个候选通过全部一票否决项
- 最终选择基于同一套评分框架，而不是只靠直觉
- 最终方案具体到足以解锁星图页和 resolve 流程的实现

---

## 阶段 3：首页推荐闭环

### 目标

让首页推荐入口成为稳定的第一步动作起点。

### 任务清单

- 搭建首页基础布局
- 搭建主推荐卡组件
- 搭建条件层组件
- 搭建辅推荐轻入口
- 实现 `GET /api/recommendations`
- 实现第一阶段推荐选择逻辑
- 返回首页第一屏结构化结果，而不是平铺推荐数组
- 在未授权定位时支持通用回退
- 将首页推荐动作接到星图页

### 验证标准

- 首页稳定展示第一屏结构化推荐结果
- 主推荐、条件层、辅推荐渲染正确
- 未授权定位时首页仍然可用
- 点击主动作能进入星图页
- 当目标数据存在时，点击次动作可进入详情流

---

## 阶段 4：星图接入与识别承接闭环

### 目标

接入选定的星图能力，并完成“点对象 -> 进入我们自己的对象流程”这一关键承接。

### 任务清单

- 基于选定的 PoC 外壳方向搭建正式星图页结构
- 接入最终选定的星图能力
- 支持拖动、缩放、对象点击等基础交互
- 以预契约状态实现第一版 `GET /api/sky-map/resolve`
- 将星图对象点击结果接入本地对象映射流程
- 打通星图 -> 详情页的跳转
- 保持底部承接区符合我们已经确认的产品交互规则

### 验证标准

- 星图可成功渲染
- 拖动、缩放、点击交互正常工作
- 至少能稳定承接星座、亮星、行星
- 匹配成功时，点击对象可稳定进入详情页流程
- 未匹配对象时，有明确的回退反馈

---

## 阶段 5：详情页与解释卡片闭环

### 目标

把“认出一个对象”变成“理解这个对象”。

### 任务清单

- 搭建详情页结构
- 搭建对象摘要组件
- 搭建解释卡片组件
- 实现 `GET /api/objects/[slug]`
- 在一次响应中聚合对象摘要与解释卡片
- 增加下一步探索入口
- 保持“返回继续探索”是主延续动作

### 验证标准

- 详情页稳定渲染对象摘要
- 解释卡片字段完整可用
- 前端不需要自己拼多次请求
- 星图 -> 详情页流程顺滑
- 详情页明确支持回到探索流程

---

## 阶段 6：工具页轻辅助闭环

### 目标

增加第一阶段轻辅助层，同时避免工具页演变成重专业中心。

### 任务清单

- 搭建工具页结构
- 搭建观测摘要组件
- 实现 `GET /api/tools/observation-summary`
- 增加场景建议和轻设置区块
- 保持工具页明确从属于首页和星图主流程

### 验证标准

- 工具页可访问且内容完整
- 能展示轻量观测摘要和场景建议
- 不会长成重参数面板
- 页面职责不与主产品闭环冲突

---

## 阶段 7：端到端整合与 MVP 打磨

### 目标

把首页、星图页、详情页、工具页连接成一个完整、可测试的 MVP。

### 任务清单

- 打通首页 -> 星图 -> 详情主闭环
- 打通工具页辅助闭环
- 补齐未匹配对象、缺少定位、空推荐等异常与回退情况
- 统一基础视觉与文案表现
- 执行关键路径回归检查
- 根据真实接入结果，判断预契约 `resolve` 是否可以升级为正式契约

### 验证标准

- 四个核心页面全部连通且可用
- 四个核心 API 都能按自身成熟度稳定返回结果
- 主要失败与回退场景都有合理反馈
- MVP 可演示、可测试，并可进入下一轮迭代
- 星图承接路径不再停留在假设层，而是基于真实选型验证成立

---

## 第一阶段范围说明

本计划有意只覆盖第一阶段 MVP。
第一阶段完成后，后续版本应在现有项目骨架之上继续开新迭代计划。

也就是说：
- 后续功能通常在现有结构上扩展
- 每一轮新迭代都不重复基础环境阶段
- 只有技术路线大改或产品形态大改，才应触发基础重构

---

## 推荐执行顺序总览

1. 项目骨架与基础环境
2. 星图候选 PoC 与方案选择
3. 首页推荐闭环
4. 星图接入与识别承接闭环
5. 详情页与解释卡片闭环
6. 工具页轻辅助闭环
7. 端到端整合与 MVP 打磨
