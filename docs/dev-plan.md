# 开发计划：Echo of Photons

## 文档目的

本文件用于定义 Echo of Photons 第一阶段 MVP 的开发计划。
它的目标不是描述整个长期项目路线，而是把当前已经确认的产品与技术决策，转化为可执行的第一版交付顺序。

本计划只覆盖第一阶段 MVP。
后续版本应在现有项目骨架之上继续增量迭代，而不是重复基础环境搭建，除非技术路线被推翻，或产品形态发生根本变化。

---

## 阶段 1：项目骨架与基础环境

### 目标

建立第一阶段可运行的工程骨架，包括前端路由、后端入口结构和数据库连接基础。

### 任务清单

- 初始化 Next.js 项目
- 建立基础目录结构：`app / features / server / data-access / components / lib`
- 搭建全局布局外壳
- 确立统一 API 返回结构
- 准备 PostgreSQL 基础连接
- 准备环境变量加载与 DB Client

### 验证标准

- 项目可以成功启动
- 首页、星图页、详情页、工具页的空路由可以访问
- 至少一个测试 API 路由返回统一结构
- 数据库连接可以成功验证

---

## 阶段 2：星图候选 PoC 与方案选择

### 目标

用轻量真实外壳验证第一轮星图候选方案，并锁定第一阶段要采用的星图能力。

### 第一轮候选顺序

1. `Aladin Lite`
2. `Stellarium Web / Web Engine`
3. `WorldWide Telescope Web Control`

### 任务清单

- 搭建一个轻量星图 PoC 外壳，而不是裸技术 demo
- 保持很轻的顶部区域、一个主星图区、一个轻底部承接区，以及约 3 个轻工具占位
- 验证固定时间与地点切换行为
- 验证对象点击行为，并查看返回的对象信息
- 验证对象名称是否能顺利进入本地 resolve 流程
- 验证默认 UI 是否能收进我们的产品方向
- 为每个候选记录一份 PoC 结论

### 一票否决项

候选方案只要出现以下任一情况，立即淘汰：

1. 不能嵌入到 Web 页面结构中
2. 不能按时间与地点控制天空变化
3. 点击对象后拿不到稳定对象名称

### 评分维度

对通过一票否决层的候选，按以下维度评分：

1. Web 接入难度
2. 时间与地点控制质量
3. 对象点击事件质量
4. 返回对象信息质量
5. UI 可裁剪程度
6. 新手认星友好度
7. 对首页 -> 星图 -> 详情闭环的支持程度

### 分数含义

- `0`：不支持或明显不适合
- `1`：勉强可用，但风险很高
- `2`：基本可用
- `3`：非常适合第一版

### 验证标准

- 三个候选方案都有可比较的 PoC 记录
- 至少一个候选通过全部一票否决项
- 最终选择基于同一套评分框架，而不是只靠直觉
- 最终方案具体到足以解锁星图页和 resolve 流程的实现

## 阶段 3：首页推荐闭环

### 目标

让首页推荐入口成为稳定的第一步动作起点。

### 任务清单

- 搭建首页基础布局
- 搭建主推荐卡组件
- 搭建条件层组件
- 搭建辅推荐轻入口
- 实现 `GET /api/recommendations`
- 实现第一阶段推荐选择逻辑
- 返回首页第一屏结构化结果，而不是平铺推荐数组
- 在未授权定位时支持通用回退
- 将首页推荐动作接到星图页

### 验证标准

- 首页稳定展示第一屏结构化推荐结果
- 主推荐、条件层、辅推荐渲染正确
- 未授权定位时首页仍然可用
- 点击主动作能进入星图页
- 当目标数据存在时，点击次动作可进入详情流

## 阶段 4：星图接入与识别承接闭环

### 目标

接入选定的星图能力，并完成“点对象 -> 进入我们自己的对象流程”这一关键承接。

### 任务清单

- 基于选定的 PoC 外壳方向搭建正式星图页结构
- 接入最终选定的星图能力
- 支持拖动、缩放、对象点击等基础交互
- 以预契约状态实现第一版 `GET /api/sky-map/resolve`
- 将星图对象点击结果接入本地对象映射流程
- 打通星图 -> 详情页的跳转
- 保持底部承接区符合我们已经确认的产品交互规则

### 验证标准

- 星图可成功渲染
- 拖动、缩放、点击交互正常工作
- 至少能稳定承接星座、亮星、行星
- 匹配成功时，点击对象可稳定进入详情页流程
- 未匹配对象时，有明确的回退反馈

## 阶段 5：详情页与解释卡片闭环

### 目标

把“认出一个对象”变成“理解这个对象”。

### 任务清单

- 搭建详情页结构
- 搭建对象摘要组件
- 搭建解释卡片组件
- 实现 `GET /api/objects/[slug]`
- 在一次响应中聚合对象摘要与解释卡片
- 增加下一步探索入口
- 保持“返回继续探索”是主延续动作

### 验证标准

- 详情页稳定渲染对象摘要
- 解释卡片字段完整可用
- 前端不需要自己拼多次请求
- 星图 -> 详情页流程顺滑
- 详情页明确支持回到探索流程

## 阶段 6：工具页轻辅助闭环

### 目标

增加第一阶段轻辅助层，同时避免工具页演变成重专业中心。

### 任务清单

- 搭建工具页结构
- 搭建观测摘要组件
- 实现 `GET /api/tools/observation-summary`
- 增加场景建议和轻设置区块
- 保持工具页明确从属于首页和星图主流程

### 验证标准

- 工具页可访问且内容完整
- 能展示轻量观测摘要和场景建议
- 不会长成重参数面板
- 页面职责不与主产品闭环冲突

## 阶段 7：端到端整合与 MVP 打磨

### 目标

把首页、星图页、详情页、工具页连接成一个完整、可测试的 MVP。

### 任务清单

- 打通首页 -> 星图 -> 详情主闭环
- 打通工具页辅助闭环
- 补齐未匹配对象、缺少定位、空推荐等异常与回退情况
- 统一基础视觉与文案表现
- 执行关键路径回归检查
- 根据真实接入结果，判断预契约 `resolve` 是否可以升级为正式契约

### 验证标准

- 四个核心页面全部连通且可用
- 四个核心 API 都能按自身成熟度稳定返回结果
- 主要失败与回退场景都有合理反馈
- MVP 可演示、可测试，并可进入下一轮迭代
- 星图承接路径不再停留在假设层，而是基于真实选型验证成立

## 第一阶段范围说明

本计划有意只覆盖第一阶段 MVP。
第一阶段完成后，后续版本应在现有项目骨架之上继续开新迭代计划。

也就是说：
- 后续功能通常在现有结构上扩展
- 每一轮新迭代都不重复基础环境阶段

## V2 第二阶段：认星体验产品化

### 背景

V1 与 V2 第一段已完成主闭环验证：首页推荐可以进入星图，StarCanvas 可以稳定展示可见星空、中文标签、目标高亮、对象点击、`resolve` 权威映射、BottomDrawer 承接与详情解释卡片。

WWT 仍保留为底层和专项验证能力，但在真实浏览器完成可见渲染验证之前，不作为 V2 主视觉层，也不阻塞 V2 主线。

### 目标

在 StarCanvas 主舞台已经可演示的基础上，把星图从“能看、能点、能进详情”推进到“新手更愿意看、更容易知道先看哪里、更能理解下一步怎么探索”。

本阶段采用 A+B 方向：
- A：StarCanvas 星图视觉层级打磨
- B：目标引导体验最小版

### 任务清单

#### 3.1 StarCanvas 星图视觉层级打磨

- 优化星点大小、亮度、色温与光晕层级
- 优化星座线透明度和层级，避免压过主要目标
- 优化中文标签层级，保持新手可读但不铺满画面
- 优化目标高亮视觉，使推荐目标更容易被第一眼发现
- 保持现有点击热区、`resolve`、BottomDrawer、详情链路不变

#### 3.2 target + source 驱动的推荐承接体验

##### 产品边界

V2 第二阶段不改变首页信息架构：
- 首页仍保持“主推荐 + 条件层 + 辅推荐”
- 不新增次推荐
- 不做观星路线系统
- 辅推荐可以进入星图，但不能抢主推荐权重

##### 目标

让首页推荐在 StarCanvas 主舞台中被明确兑现。用户从首页进入星图后，系统不仅要带到星图页，还要让推荐对象在星图中可见、可辨认、可点击、可进入详情。

##### URL 上下文规则

- `target`：核心参数，决定 StarCanvas 高亮哪个对象
- `source`：增强上下文，决定高亮强度和 BottomDrawer 引导语气
- `source` 只作为前端路由上下文，不进数据库、不改 API 契约

##### source 行为

- `source=primary`：主推荐入口
  - 触发强高亮
  - 显示画面轻提示“先看这里”
  - BottomDrawer 使用“今晚先找 {target}”和完整理由

- `source=secondary`：辅推荐入口
  - 触发轻高亮
  - 不显示“先看这里”
  - BottomDrawer 使用“也可以看看 {target}”和简短理由

- 缺失 `source`：默认按 `primary` 处理，兼容旧链接 `/sky-map?target=...`
- 非法 `source`：不报错，默认按 `primary` 处理

##### 验证标准

- 主推荐进入星图后，目标第一眼可见并触发强高亮
- 辅推荐进入星图后，目标可定位但视觉权重低于主推荐
- 缺失或非法 `source` 不导致页面报错
- `target` 未知时安全回退，不错误高亮、不制造假入口
- 点击对象后仍稳定走 `resolve -> BottomDrawer -> /objects/{slug}` 链路

## V3 第一阶段：真实定位推荐

### 目标

让首页推荐从固定文案升级为基于用户当前位置与当前时间的真实可见性推荐，同时保持现有 StarCanvas、BottomDrawer、详情页链路不变。

### 任务清单

- 选定并接入本地天文位置计算能力
- 定义内容对象池、推荐对象池与识别对象池的边界
- 在 `GET /api/recommendations` 中接入真实位置与时间计算
- 保持推荐结果可被首页、StarCanvas、BottomDrawer、详情页完整承接
- 在首页接入浏览器定位授权与静默回退逻辑

### 验证标准

定位推荐闭环应满足：
- 允许定位时，首页推荐基于真实 `lat/lng + 当前时间` 返回主推荐与辅推荐
- 拒绝定位、超时、失败或浏览器不支持时，首页静默回退到通用推荐
- 首页推荐结果仍可稳定承接到 StarCanvas 高亮、BottomDrawer 引导与详情页
- 参数校验、错误结构与通用回退行为保持一致

### 最小任务顺序

1. 调研并验证天文位置 / 可见性计算方案
2. 升级 `GET /api/recommendations` 为真实可见性推荐
3. 首页接入浏览器定位并完成静默回退

---

## V3 第二阶段：详情页动态观测与延续探索

### 背景

V3 第一阶段已经完成真实定位推荐：首页可以基于用户定位和当前时间推荐更适合观察的对象，且推荐结果已能稳定承接到 StarCanvas、BottomDrawer、`resolve` 与详情页。

当前详情页的主要问题不再是“能不能打开”，而是内容重心仍偏解释性，缺少对“今晚能不能看、往哪看、什么时候更适合看”的动态观测承接。

### 目标

把详情页从“解释页”升级为“动态观测 + 静态解释”的结构化页面，同时让详情页不再是探索终点，而能继续把用户送回星图做下一步观察。

### 任务清单

#### 1. 详情页结构升级

- 将详情页结构调整为：对象标题区 -> 动态观测卡 -> 解释卡 -> related 承接区 -> 返回继续探索
- 保留 `ObjectSummary` 作为对象页头，但视觉权重低于动态观测卡
- 保留现有解释卡，不删除 `whatIsIt / whyWatchIt / whatNext` 的解释性内容

#### 2. 动态观测卡 V1

- 在详情页第一屏新增动态观测卡，优先展示当前观测意义，而不是百科解释
- 动态观测卡 V1 只展示 6 项核心信息：
  - 当前状态：现在可见 / 即将升起 / 当前不可见
  - 方位：优先使用 8 方位人话表达
  - 高度：例如 `高度 42°`
  - 升起时间
  - 落下时间
  - 今晚建议：一句结论型建议
- 同一张卡同时服务行星、亮星、星座；星座允许按中心点坐标计算并做更柔和文案解释

#### 3. 离散时间切换 V1

- 动态观测卡内部提供离散时间切换，不做自由时间选择器
- 第一版固定 3 个时间点：`现在`、`1小时后`、`今晚稍晚`
- `今晚稍晚` 规则：
  - 当前时间早于 `22:00` 时，取当天 `22:00`
  - 当前时间晚于 `22:00` 时，取当前时间 + 2 小时
- 切换时间后只刷新动态观测卡内的状态、方位、高度、升起/落下时间与今晚建议
- 切换时间后不刷新标题区、解释卡、related 区与返回探索动作

#### 4. related 承接区与 `source=related`

- 将 `whatNext` 从纯文本方向升级为结构化 related 承接
- 第一版 `whatNext` 结构：
  - `summary: string`
  - `relatedObjects: Array<{ slug, nameZh }>`
- related 第一版只允许引用内容对象池中的对象，确保星图、`resolve`、详情承接都接得住
- 详情页 related 区最多显示 1 到 3 个对象，不发展成新的推荐列表
- 点击 related 对象跳转到：`/sky-map?target={slug}&source=related`
- `source=related` 的产品语义是“延续入口”，不是首页推荐入口
- 优先级规则：`selectedObject > primary > related > secondary > 普通对象 > 背景`
- BottomDrawer 文案语气：`接下来可以找 {target}`

### 验证标准

本阶段完成后应满足：
- 详情页第一屏优先回答“现在能不能看、往哪看、什么时候更适合看”
- 动态观测卡可在 3 个离散时间点之间切换，且状态变化有明确意义
- 解释卡仍保留，但视觉与信息优先级低于动态观测卡
- related 对象可以稳定跳转到星图，并以 `source=related` 被正确承接
- 点击 related 进入星图后，不应表现成与首页主推荐同级的强引导
- 详情页不退化为专业参数面板，不在第一版引入轨迹图、自由时间选择器、光污染评分等重功能

### 明确不做

- 不做自由时间选择器
- 不做 24 小时时间轴
- 不做星图全局时间上下文共享
- 不做星图随时间实时重排
- 不做设备朝向联动
- 不做轨迹图、光污染评分、专业参数表式展示
- 不允许识别对象池但未进入内容对象池的对象直接进入 related 承接

### 建议最小任务顺序

1. 详情页结构升级 + 动态观测卡静态骨架
2. 动态观测卡接入当前时刻观测数据
3. 接入离散时间切换
4. 结构化 related 承接 + `source=related` 星图联动

## V3 第三阶段：搜索入口与主动探索

### 背景

V3 第二阶段已经建立了详情页动态观测、时间共享上下文 V1 与 related 承接闭环。用户现在可以被推荐带着走，也可以顺着 related 继续探索。

下一步需要补上“主动探索”入口：用户不应只能接受系统推荐或 related 承接，还应能够主动搜索一个对象，并让星图把它明确指出来。

### 目标

建立搜索入口 V1，让用户在星图页主动指定目标对象；搜索命中后，星图以 `source=search` 进入定位态，目标获得明显高亮，并被轻量带到更易观察的位置。

### 任务清单

#### 1. 星图页搜索入口 V1

- 第一版搜索入口只放在星图页顶部
- 搜索入口保持轻量，不长成独立工具中心或全屏搜索层
- 搜索结果列表最多显示 5 条结果
- 空结果提示保持极轻，例如“没找到可定位对象”

#### 2. 搜索对象池范围

- 第一版搜索只对用户承诺两层对象：
  - 可完整探索对象：有详情、有星图定位、有承接链路
  - 可搜索可定位对象：不一定有完整详情，但可稳定在星图中定位
- 第一版不承诺“搜全宇宙”，不直接将外部宇宙对象作为产品主结果层
- 搜到的对象必须能够被当前星图或详情承接，不允许搜到却接不住

#### 3. `source=search` 承接规则

- 点击搜索结果后，不离开星图页，进入：`/sky-map?target={slug}&source=search`
- 如果当前已有 `timeContext`，搜索结果继续带上该时间上下文
- `source=search` 的产品语义是“用户主动指定目标”，不是系统推荐，也不是 related 延续
- BottomDrawer 使用“正在找 {target}”语气
- `source=search` 不显示“先看这里”文字提示

#### 4. 搜索高亮与轻聚焦

- 视觉优先级调整为：`selectedObject > search > primary > related > secondary > 普通对象 > 背景`
- `search` 高亮强于 `primary`，但不使用教程式引导文案
- 搜索命中后，星图不只高亮目标，还应轻量带动视图，让目标进入更易观察的位置
- 搜索命中后不自动进入 `selectedObject` 状态，用户仍需点击对象确认

### 验证标准

本阶段完成后应满足：
- 用户可以在星图页主动搜索对象，而不只被推荐带着走
- 搜索结果点击后，目标以 `source=search` 进入星图定位态
- `source=search` 的高亮明显强于 `primary`，但不出现“先看这里”
- 搜索命中后，星图视图会发生轻量聚焦变化，而不只是出现一个高亮点
- 搜索结果可继续走 BottomDrawer -> 点击对象 -> 查看详情 链路
- 第一版搜索不承诺全宇宙搜索，只承诺“搜到的对象要么能完整探索，要么能稳定定位”

### 明确不做

- 不做全屏搜索页
- 不做复杂筛选、分类 tab 或高级搜索
- 不让搜索结果默认跳详情页
- 不把外部宇宙目录直接作为第一版对用户承诺的主结果层
- 不在本阶段引入设备朝向联动
- 不把搜索实现成新的推荐系统

### 建议最小任务顺序

1. 星图页顶部搜索入口 + 结果列表骨架
2. 搜索对象池接入与基础匹配
3. `source=search` 承接 + BottomDrawer 语气
4. 搜索命中后的轻聚焦

## V3 第四阶段：对象池扩容 V1

### 背景

V3 第三阶段已经建立了主动搜索入口，用户可以主动指定目标并让星图进入 `source=search` 定位态。

但当前搜索与星图仍主要围绕 10 个核心对象运转，距离“很多星星”“画面更像一片可探索天空”还有明显差距。

### 目标

将当前“10 个核心对象演示层”扩展为“约 200 个可搜索可定位对象层”，其中少量对象可完整探索，更多对象至少可稳定搜索和定位。

### 任务清单

#### 1. 本地亮星对象数据层

- 第一版优先引入一份本地亮星对象数据层，而不是先建新数据库表
- 数据形态优先使用 `ts` 常量数据，而不是实时外部搜索 API
- 第一版优先服务搜索与 StarCanvas，不要求所有对象立即进入完整详情体系
- 推荐放置为独立天文数据层，而不是散落在组件文件中

#### 2. 第一批对象规模与类型

- 第一批目标规模为 100~300 个，推荐落在 200 个左右
- 推荐配比：
  - 约 120 个亮星
  - 约 30 个主要星座对象
  - 约 50 个高认知其他目标
- 第一刀优先从亮星层开始，不要求星座与其他目标同步全部落地

#### 3. 对象分层与承接边界

- 保留当前 10 个核心对象作为“可完整探索对象”
- 新扩对象优先进入“可搜索可定位对象”层
- 第一版不要求所有扩容对象都拥有完整详情页、解释卡与 related 承接
- 搜到的对象至少要满足：可搜索、可在星图定位、不会命中后完全接不住

#### 4. 搜索与 StarCanvas 共用对象层

- 搜索与 StarCanvas 优先共用同一份本地对象数据层
- 不允许搜索结果池和星图可定位池长成两套不同世界
- 扩容后，StarCanvas 继续保持三层表现：核心对象、扩展可定位对象、背景星点
- 扩展对象在视觉上应弱于核心对象，但强于纯背景点

### 验证标准

本阶段完成后应满足：
- 搜索结果池不再只有 10 个对象
- 星图中可定位对象数量明显增加，画面探索密度提升
- 扩容对象与当前搜索/target/source/timeContext 链路兼容
- 扩容对象不强迫全部拥有完整详情承接
- 本地对象层可被后续设备朝向阶段继续复用

### 明确不做

- 不把第一批扩容直接做成几千上万对象
- 不把实时外部 API 作为第一版搜索主线
- 不要求所有扩容对象同步拥有完整详情页
- 不在本阶段直接进入设备朝向联动
- 不先为扩容对象重做数据库结构，除非局部最小需求明确出现

### 建议最小任务顺序

1. 本地亮星对象数据层骨架
2. 搜索对象池接入亮星扩容数据
3. StarCanvas 接入扩展亮星层
4. 评估标签密度与点击承接边界

## V4 第一阶段：朝向驱动天空视图 V1

### 背景

对象池扩容后，星图已经不再只是 10 个核心对象的演示层，而开始具备更明显的可探索密度。

下一步不再只是增加对象数量，而是要让手机端用户真正获得“站在地球上抬头看天空”的视角体验：手机朝哪，画面就朝哪，显示那个方向天空中的对象分布。

### 目标

建立朝向驱动天空视图 V1：在手机端，以用户当前位置与当前时间为基础，使用设备朝向作为视野中心，实时显示该方向天空中的对象分布。

### 任务清单

#### 1. 朝向模式开关

- 朝向驱动不默认强开，第一版采用手动开启的“朝向模式”
- 只在移动端设备上提供明确入口
- 普通星图模式与朝向模式需要可切换

#### 2. 设备方向权限与回退

- 用户开启朝向模式后，按平台要求申请设备方向权限
- 权限成功：进入朝向驱动视图
- 权限失败、设备不支持或浏览器不支持：静默回退到普通星图模式，并给出轻量反馈
- 桌面端默认保持普通模式，不强行模拟朝向视图

#### 3. 视野中心模型

- 星图不以“宇宙俯视图”方式转动，而以“观察者视线窗口”方式更新
- 每个对象仍先根据时间 + 地点计算真实 alt/az
- 再以设备朝向作为当前视野中心，把附近天空投影到屏幕上
- 视角变化不等于对象真实天文位置变化，而是观察窗口变化

#### 4. 与现有链路共存

- 朝向模式需要兼容当前：搜索、target/source、timeContext、BottomDrawer、selectedObject
- 第一版不要求把所有模式都做成复杂组合，但不能破坏现有主链路
- 搜索与高亮逻辑在朝向模式中仍然成立

### 验证标准

本阶段完成后应满足：
- 手机端用户开启朝向模式后，画面会随着设备朝向变化而更新
- 变化的是“当前可见天空窗口”，不是简单整张画布旋转
- 当前时间、地点与对象分布仍然保持一致
- 权限失败或设备不支持时，能平稳退回普通模式
- 搜索/高亮/BottomDrawer/点击确认链路不被朝向模式破坏

### 明确不做

- 不在第一版实现复杂校准系统
- 不在第一版做全自动无提示进入朝向模式
- 不在桌面端强行模拟移动端朝向体验
- 不把朝向模式做成新的专业天文参数面板
- 不与 WWT 主线重新绑定，优先基于当前 StarCanvas 主舞台推进

### 建议最小任务顺序

1. 朝向模式开关与移动端入口
2. 设备方向权限请求与失败回退
3. 以设备朝向为视野中心的 StarCanvas 视图更新
4. 搜索/高亮/BottomDrawer 在朝向模式下的兼容验证
