# 技术规格：Echo of Photons

## 文档目的

本文件用于明确 Echo of Photons 第一阶段的技术主线、系统结构、数据边界和实现重点，作为后续设计、开发计划与编码执行的直接依据。

当前版本优先沉淀已经拍板的 A 级主线决策，后续再继续补充数据库、API、项目结构和实现细节。

---

## 1. 技术路线总览【A 级】

### 1.1 当前项目阶段定位

Echo of Photons 的最终主形态是移动端 App，但第一阶段交付形态为 Web。

第一阶段 Web 不是一次性验证 Demo，而是一个可继续演进、可承接后续 App 化的中间态产品。

### 1.2 第一阶段技术主线

当前已确认的第一阶段技术主线如下：

1. 产品结构采用标准页面式结构，而不是把所有体验压缩在单一流式页面中。
2. 星图能力优先接入成熟能力做集成，而不是从零搭建底层星图引擎。
3. `今日适合看什么` 第一阶段采用轻推荐方案，优先解决“用户打开后该做什么”的问题，而不是一开始做成重观测条件系统。
4. 系统形态采用轻后端 + 轻数据库方案，支持推荐内容、天体解释卡片和后续扩展，但不在第一阶段搭建过重的全栈体系。
5. Web 前端主栈采用 Next.js + React 路线，作为第一阶段页面式应用的实现基础。
6. 轻后端采用 Next.js 内聚式方案，不在第一阶段拆分独立后端服务。
7. 数据层采用正经轻数据库方案，而不是本地 JSON 或一次性文件存储。
8. 正式数据库主线采用 PostgreSQL。
9. 解释卡片作为内容承接层对象，第一阶段独立成表，而不是并入天体主对象表。
10. 第一阶段数据库不预埋未来功能表，只为已确认的 MVP 闭环建立最小表集。
11. 第一阶段从一开始就走标准 PostgreSQL 路线，不采用本地轻替代再迁移的双轨方案。

### 1.3 技术主线判断

这条路线的核心思路是：

- 把工程投入集中在产品主闭环上
- 把复杂底层能力交给成熟能力承担
- 把第一阶段 Web 做成可验证、可演进、可迁移的结构
- 让数据层刚好够支撑内容与推荐，而不是过早变成复杂业务系统
- 让页面层与轻 API 层保持靠近，降低第一阶段联调与维护成本
- 用正经数据库保证后续 App 化和内容扩展时不需要推翻数据底座
- 采用 PostgreSQL 作为长期主线，避免第一阶段后再做数据库迁移
- 将天体对象与内容承接对象分开，保持对象事实与内容表达边界清楚

这样更符合 2-3 个月项目周期，也更符合当前产品真正需要被验证的部分：

- 用户是否能顺利完成识别
- 用户是否愿意继续查看解释卡片
- 用户是否会被首页推荐引导进入探索

## 2. 产品结构与前端实现边界【A 级】

### 2.1 需要先拆开的两个概念

在本项目中，必须明确区分以下两个层次：

1. 产品交互结构
2. 前端技术实现方式

`SPA` 和 `MPA` 首先是前端实现概念，不应直接代替产品结构判断。

因此，本项目当前已经确认的是：

- 产品结构上采用页面式应用结构
- 前端主栈采用 Next.js + React，后续继续细化具体版本与目录组织方式
- 轻后端以内聚式方式落在 Next.js 体系内，不额外拆独立服务

### 2.2 第一阶段页面式结构

第一阶段 Web 产品结构当前确定为四类核心页面：

1. 首页
   - 承担 `今日适合看什么`
   - 承担观测建议与入口分发
   - 承担第一次打开时的引导作用

2. 星图页
   - 承担主要识别行为
   - 是用户完成“看到什么 -> 对应到什么”的主场景

3. 天体详情页
   - 承担解释卡片展开
   - 负责从识别结果延伸到理解与继续探索

4. 工具页
   - 承担天气、观测辅助、设置等工具型能力
   - 第一阶段可先轻量存在，为后续扩展预留边界

### 2.3 当前页面职责拍板

基于当前讨论，第一阶段四类页面的职责边界进一步明确为：

- 首页：负责激发行动，回答“我今天先看什么”
- 星图页：负责承接识别，回答“它到底在哪、我看到的是什么”
- 天体详情页：负责解释与继续探索，回答“它是什么、为什么值得继续看”
- 工具页：负责轻辅助能力，不承担主识别与主引导职责

这意味着第一阶段不把首页、星图、详情和工具能力揉成一个混合页面，而是保持清晰的页面分工。

### 2.3 为什么不用单屏流式结构

当前不推荐把首页、识别、详情、辅助能力全部揉进一个单屏结构，原因包括：

- 会削弱首页引导的独立价值
- 会让识别路径与内容承接边界模糊
- 会让后续 App 化时信息架构不稳定
- 会导致页面职责不清，后续迭代容易堆叠复杂度

## 3. 星图能力实现策略【A 级】

### 3.1 推荐方案

第一阶段采用成熟星图能力集成方案。

也就是说，本项目第一阶段不把主要工程投入放在：

- 自研星图绘制引擎
- 自研底层天体关系计算体系
- 自研完整天空数据可视化基础设施

而是优先使用成熟的星图/天文数据能力作为底层支撑，在其上构建产品体验层。

### 3.2 为什么这样选

因为当前项目要验证的不是“我们能不能从零造一套星图系统”，而是：

- 用户能不能快速认星
- 用户认出来后有没有继续探索的动力
- 首页推荐能不能把人顺利带进使用路径

如果第一阶段过早投入底层能力建设，会直接带来：

- 周期失控
- 调试复杂度上升
- 正确性验证成本上升
- 产品层体验打磨时间被压缩

### 3.3 第一阶段工程重点

在采用成熟能力集成的前提下，第一阶段我们自己的工程重点应放在：

1. 识别路径设计
2. 识别结果与解释卡片衔接
3. 首页推荐到星图探索的引导路径
4. 页面结构与后续 App 迁移的一致性

### 3.4 风险提醒

该路线虽然更稳，但也存在需要后续重点评估的风险：

- 第三方星图能力是否足够可控
- 定位、方向、时间与地点映射是否满足体验要求
- UI 自定义空间是否足够支撑产品差异化
- 后续 App 化时是否存在能力复用障碍

### 3.5 第一阶段星图能力选型标准

在已经确认“优先采用可嵌入组件型星图能力”的前提下，第一阶段进一步采用以下选型标准：

1. 优先选择可嵌入组件型能力，不优先选择完整独立型网页星图，也不走半自研显示层路线
2. 方案必须愿意服务产品流程，而不是让产品去迁就它
3. 方案至少稳定覆盖第一阶段识别范围：星座、亮星、行星
4. 方案必须支持随时间和地点变化的天空展示
5. 方案必须支持基础交互，尤其是对象点击与结果承接
6. 方案应允许裁剪不需要的专业信息，避免第一阶段界面过重
7. 方案接入成本和调试风险必须可控，不能吞掉首页、卡片与推荐主线的开发时间
8. 方案不应破坏首页 -> 星图 -> 详情页这条主路径，也不应把用户锁进它自己的独立逻辑里

### 3.6 方案排除红线

第一阶段遇到以下情况时，应优先排除该星图方案：

- 点中对象后，无法稳定映射到我们自己的 `celestial_objects`
- 方案自身产品感过强，接入后像另一个完整软件
- 专业信息过重且难以裁剪
- 接入与改造成本过高，文档、事件或状态接入明显不顺
- 与首页激发、星图承接、详情解释这条页面结构天然冲突

### 3.7 第一阶段方案试用的 3 个必测场景

后续评估具体候选方案时，优先用以下 3 个场景做试用验收：

1. 首页推荐跳进星图：用户从“今晚先看什么”进入星图后，能进入一个合理的目标视角或探索入口
2. 星图点中对象进入详情卡片：对象点击结果能被我们稳定接管，并映射到自己的解释卡片页
3. 新手自由拖动探索：用户不完全按推荐走时，仍然能在拖动、缩放、点选中保持清晰而不过载的体验

其中第 2 条属于一票否决级场景；若方案无法稳定承接对象点击后的详情流程，则第一阶段不适合采用。

这些将进入后续技术选型与实现细节部分继续展开。

### 3.8 第一轮候选方案来源优先级

第一轮候选方案不建议铺得过宽，而应优先控制在 2-3 个以内。
候选来源优先级收敛为：
1. 商业 SDK / 组件型方案
2. 开源 Web 星图库
3. 暂不优先看完整产品型网页星图

建议第一轮候选结构为：1-2 个商业 SDK / 组件，加 1 个开源 Web 星图库作为对照。

### 3.9 第一轮快速试选顺序

第一轮评估具体候选方案时，不先看“功能多不多”或“画面炫不炫”，而优先按以下顺序筛选：
1. 先看接入形态：它更像可嵌入能力，还是更像一个完整独立产品
2. 再看对象点击：是否能稳定拿到 `name`，最好同时拿到 `type`
3. 再看时间与地点控制：天空是否能按用户上下文变化
4. 再看默认 UI 是否能轻裁剪
5. 最后再用 3 个必测场景走完整体验

### 3.10 第一阶段对象承接最低标准

第一阶段星图底层能力在对象承接这一层的最低可接受标准为：
- 点中对象后，能稳定拿到对象名字
- 最好同时拿到对象类型
- 由本系统的 `GET /api/sky-map/resolve` 负责后续映射

第一阶段优先追求名称体系尽量直连：
- 第三方返回的主流名称与本地 `celestial_objects` 尽量对齐
- 以直连映射为主
- 只允许极少量兜底映射，不把第一版做成复杂别名清洗层

### 3.11 第一阶段 UI 改造边界

第一阶段只接受可轻裁剪的星图方案，不接受必须经过中度界面改造才勉强能融入产品的候选。
如果一个方案默认 UI 过重，且需要大量隐藏、重排、对抗其自身产品逻辑，原则上不适合进入第一版。

## 4. 首页推荐能力策略【A 级】

### 4.1 推荐方案

`今日适合看什么` 第一阶段采用轻推荐方案。

### 4.2 第一阶段目标

这个模块在第一阶段的首要职责不是成为专业观测决策系统，而是成为用户每次打开产品时的低门槛入口。

它需要优先回答的是：

- 我今天打开后先做什么
- 今晚有没有值得我看的对象
- 我接下来怎么进入星图探索

### 4.3 第一阶段建议内容范围

第一阶段推荐内容优先围绕以下信息组织：

- 当前时间段值得关注的亮星、行星、星座
- 与季节或近期天象相关的轻量提示
- 与用户现实观测动作直接相关的引导文案
- 进入星图页或详情页的直接入口

### 4.4 第一阶段暂不做重条件系统

第一阶段不建议将以下能力做成主流程核心：

- 复杂天气评分
- 多维可见度模型
- 专业级观测条件分级系统
- 过重的自动化推荐引擎
- 用户级实时生成后再落库的推荐系统

原因不是这些能力没有价值，而是它们更适合作为后续增强项，或以辅助信息方式轻量接入，而不是压住 MVP 主闭环。

### 4.5 后续扩展空间

后续若验证首页推荐确实对留存和探索路径有明显作用，可继续增强：

- 天气与云量信息
- 城市光污染与可见度提示
- 更细的时间窗口建议
- 个性化关注对象推荐
- 基于用户地点与使用行为的更细推荐策略

### 4.6 首页与星图页的当前边界

首页与星图页第一阶段边界当前明确如下：

- 首页负责激发，不承担完整识别过程
- 首页第一屏采用推荐卡片优先结构
- 推荐卡片只回答“今晚先看什么、为什么值得看”
- 首页中的主动作是 `去星图找它`，而不是在首页内完成主要识别
- 星图页负责真正的查看、定位、点击和识别承接
- 星图页不重复承担首页整套推荐叙事

也就是说，首页负责点火，星图页负责接住动作，不把两边揉成一个半推荐半工具的混合页面。

### 4.7 首页第一屏推荐与条件层结构

首页第一屏当前进一步收敛为以下结构：
1. 一个主推荐卡片，作为绝对视觉中心
2. 一层贴近主推荐的轻条件说明
3. 一个同主题的辅推荐轻入口

主推荐负责：
- 给出今晚最值得先开始的目标
- 给出一句短理由
- 提供 `去星图找它` 作为主动作
- 提供 `先了解一下` 作为次动作

辅推荐负责：
- 不是第二个独立推荐
- 而是主推荐的同主题补充
- 采用更具体的抓手表达
- 不带明显动作按钮，只作为轻入口存在

条件层负责推荐依据，不发展成首页天气面板。
其内部再分为两层：
- 依据层：偏客观条件描述，例如天空晴朗程度与月光影响
- 行动层：偏鼓励行动的建议，帮助用户知道今晚更适合如何开始

## 5. 架构概览【A 级】

### 5.1 当前建议的逻辑分层

```text
[Web Frontend]
  |- Home Page（今日适合看什么 / 入口分发）
  |- Sky Map Page（星图识别）
  |- Object Detail Page（解释卡片）
  |- Tools Page（天气 / 辅助 / 设置）
          |
          v
[Application Layer]
  |- Recommendation Selection Logic
  |- Object Info Aggregation
  |- User Context Handling（时间 / 地点 / 场景）
          |
          v
[Next.js Integrated Backend Layer]
  |- Route Handlers / Server Actions
  |- Lightweight API Layer
  |- Object Content Store Access
  |- Recommendation Store Access
          |
          v
[Capability Layer]
  |- Star Map Capability / Astronomy Data
  |- Weather / Observation Condition Data（后续可接入）
  |- Content Source / Object Metadata
```

### 5.2 架构原则

补充当前实现职责分配判断：

- 首页偏内容引导型页面，优先承担推荐结果展示与入口分发
- 星图页偏高交互页面，优先承担主要识别操作
- 详情页偏内容承接页，以解释卡片为主体，局部承接继续探索动作
- 工具页偏轻辅助页，第一阶段不发展成专业工具中心

当前架构设计遵循以下原则：

- 页面职责清楚，不把所有能力堆到一个视图中
- 产品层逻辑与底层星图能力解耦
- 首页推荐、星图识别、解释卡片各自有明确边界
- 为后续 App 化保留迁移空间
- 后端与数据库先围绕 MVP 内容对象建设，不提前扩成重系统
- 第一阶段以前后端同仓、同栈、近距离联调为优先
- 数据层采用正经数据库，但 schema 与业务范围保持克制
- 推荐表作为结果层存在，推荐依据不全部堆进单表中

## 6. 数据库设计【A 级】

### 6.1 数据库总体原则

第一阶段已确认采用正经轻数据库方向，而不是 JSON 文件或临时本地存储。

这意味着数据库设计的目标不是一开始覆盖完整天文业务，而是先稳定支撑 MVP 主闭环中的内容对象和推荐组织。

当前数据库设计遵循以下原则：

- 使用正经关系型数据库承载核心内容对象
- 第一阶段只建支撑 MVP 的最小表结构
- 不为未来不确定能力预埋大量空表和复杂关系
- 保持后续 App 阶段可以直接沿用这层数据底座
- 正式数据库主线采用 PostgreSQL
- 天体主对象与解释卡片对象分表设计
- 推荐记录有时效性，过期失效但记录保留
- 推荐类型和适用条件分开，不混成一个字段
- 第一阶段本地开发与后续部署统一走 PostgreSQL，不走双轨替代方案

### 6.2 第一阶段最小表集

第一阶段当前收敛为三张核心主表：

1. `celestial_objects`
2. `object_cards`
3. `daily_recommendations`

不额外建立未来功能表，也不提前拆分推荐系统相关的多套子表。

### 6.3 表一：`celestial_objects`

职责：承载天体对象本体，只负责对象身份与基础分类，不承担解释内容或推荐逻辑。

最小字段集：

- `id`
- `slug`
- `name_zh`
- `name_en`
- `object_type`
- `is_active`
- `created_at`
- `updated_at`

字段说明：

- `slug`：稳定对象标识，用于路由、推荐引用和接口查询，例如 `jupiter`
- `name_zh` / `name_en`：对象中英文名称
- `object_type`：第一阶段基础分类字段，先不独立拆分类体系；枚举值优先包含 `constellation`、`bright_star`、`planet`
- `is_active`：是否进入第一阶段可用范围

示例：

```json
{
  "id": 1,
  "slug": "jupiter",
  "name_zh": "木星",
```

### 6.4 表二：`object_cards`

职责：承载天体对象被识别后的解释卡片内容，作为内容承接层存在，服务于 `celestial_objects`，但不并入对象本体表。

当前判断：

- 第一阶段一对象一条主卡片
- 第一阶段先只服务 `celestial_objects`
- 字段设计保持克制，但不写死到只适合非常窄的表达形式

最小字段集：

- `id`
- `object_id`
- `what_is_it`
- `why_watch_it`
- `what_next`
- `created_at`
- `updated_at`

字段说明：

- `object_id`：关联到 `celestial_objects.id`
- `what_is_it`：它是什么
- `why_watch_it`：为什么值得看
- `what_next`：还能继续看什么，用于承接兴趣，而不让卡片停在静态说明

### 6.5 表三：`daily_recommendations`

职责：作为首页结果层推荐表存在，承载带时效性的推荐记录。推荐失效后记录保留，首页只读取当前有效的推荐。

当前判断：

- 一天可以有多条推荐
- 推荐有很强时间性
- 过期后失效，但记录保留
- 第一阶段支持多类型推荐，不只推荐天体对象
- 推荐类型和适用条件分层理解，而不是强行复用一个字段
- 适用场景第一阶段先单值，并允许为空

第一阶段推荐类型优先支持：

- `object`
- `time_window`
- `location`
- `direction`

最小字段集：

- `id`
- `title`
- `reason`
- `recommendation_type`
- `target_ref`
- `starts_at`
- `ends_at`
- `scene_type`
- `sort_order`
- `status`
- `created_at`

### 6.6 数据库设计当前边界

第一阶段暂不进入以下设计：

- 独立标签表 / 关联表
- 用户收藏、观测记录、行为埋点等未来功能表
- 推荐算法结果自动落库

- 复杂天气和可见度模型表

这些能力后续如果进入产品主线，再按页面和接口真实需要继续反推设计。

## 7. API 设计方向【A 级，待补充】

第一阶段 API 设计应围绕 Next.js 内聚式轻后端思路展开。

也就是说，接口层优先承担：

- 首页推荐内容获取
- 天体详情与解释卡片获取
- 星图对象映射结果查询
- 观测辅助信息获取（可先轻量）

- 基于时间 / 地点 / 场景等必要上下文的推荐筛选

当前职责进一步明确为：

- 前端负责收集必要上下文并展示结果
- 接口层负责集中执行首页推荐筛选逻辑
- 第一阶段不把推荐筛选规则散落在首页页面代码中
- 后续如果引入天气、城市或更多场景规则，仍优先沿接口层集中扩展

第一阶段不建议在接口层提前引入复杂用户体系、重运营系统或高耦合推荐引擎。

### 7.1 第一阶段统一返回结构

第一阶段接口统一采用如下返回结构：

- 成功：`{ code: 0, data, message: "ok" }`
- 失败：`{ code, data: null, message }`

第一阶段建议先使用克制的错误码集合：

- `0`：成功
- `4001`：请求参数不合法
- `4041`：对象不存在
- `5001`：服务端内部错误

### 7.2 第一阶段核心接口清单

第一阶段最小闭环接口清单收敛为以下 4 个：

1. `GET /api/recommendations`：首页推荐列表
2. `GET /api/sky-map/resolve`：星图对象映射
3. `GET /api/objects/[slug]`：详情页聚合数据
4. `GET /api/tools/observation-summary`：工具页轻辅助摘要

### 7.3 首页推荐接口约定

`GET /api/recommendations` 第一阶段支持位置上下文，但不得依赖定位权限才能工作。
当缺少定位信息时，系统仍需基于当前时间返回可展示的通用推荐。

第一阶段请求参数：

- `lat`：可选
- `lng`：可选
- `sceneType`：可选
- `limit`：可选

第一阶段筛选优先级：

1. 先按当前时间有效性筛选
2. 如果传入 `sceneType`，优先匹配场景
3. 如果传入 `lat/lng`，作为轻量位置上下文参与推荐增强
4. 如果缺少场景或位置上下文，回退到通用推荐
5. 最后按 `sortOrder` 取前 `limit` 条

首页推荐返回结构保持轻量，优先只返回首页展示所必需的字段：
- `id`
- `title`
- `reason`
- `recommendationType`
- `targetRef`
- `action`

### 7.4 星图对象映射接口约定

`GET /api/sky-map/resolve` 负责把现成星图能力返回的对象信息映射到本系统对象。
第一阶段优先承接 `name` 与 `type` 这两个最稳定的映射输入。

第一阶段请求参数：

- `name`：必填
- `type`：可选

返回结果中：
- 匹配到对象时返回 `matched: true` 与对象摘要
- 未匹配到对象时返回 `matched: false`，这属于业务结果，不属于系统报错

### 7.5 对象详情接口约定

`GET /api/objects/[slug]` 第一阶段采用聚合接口方式。
一次返回详情页所需的对象本体信息与解释卡片信息，不拆成多个请求让前端自行拼装。

第一阶段返回结构包含：
- `object`：对象本体摘要
- `card`：解释卡片内容

### 7.6 工具页轻辅助接口约定

`GET /api/tools/observation-summary` 服务于工具页第一阶段的轻辅助定位。
它返回轻量观测摘要，不发展成复杂天气评分系统或专业观测参数中心。

第一阶段请求参数：
- `lat`：可选
- `lng`：可选
- `sceneType`：可选

第一阶段返回结构优先只包含：
- `summary`
- `sceneSuggestion`
- `weatherHint`

本节将在数据库对象与页面字段进一步明确后补全具体契约。

## 9. 当前结论【A 级】

当前已经确认的第一阶段技术主线为：

- 最终主形态是 App，但第一阶段先做 Web
- 第一阶段 Web 是中间态产品，不是一次性 Demo
- 产品结构采用标准页面式结构
- 星图能力优先采用成熟能力集成
- `今日适合看什么` 采用轻推荐方案
- 第一阶段采用轻后端 + 轻数据库
- Web 前端主栈采用 Next.js + React
- 轻后端采用 Next.js 内聚式方案
- 数据层采用正经轻数据库方案
- 正式数据库主线采用 PostgreSQL
- 解释卡片作为内容承接层对象独立成表
- 第一阶段数据库只建立三张核心主表：`celestial_objects`、`object_cards`、`daily_recommendations`
- 第一阶段从一开始就走标准 PostgreSQL 路线
- 首页负责激发，星图页负责承接识别，详情页负责解释与继续探索，工具页只做轻辅助中心
- 首页第一屏采用推荐卡片优先结构，主动作是 `去星图找它`
- 第一阶段不自研天文位置计算
- 第一阶段优先接现成星图界面能力，而不是自己做轻星图外壳
- PostgreSQL 落地路线为：开发期本地 Docker PostgreSQL，部署期正式托管 PostgreSQL
- 首页推荐与地点/时间等必要上下文筛选由接口层集中负责，前端负责传参与展示
- 首页第一屏采用“主推荐 + 条件层 + 辅推荐”的结构，条件层不发展成天气面板
- 星图底层能力第一轮优先看商业 SDK / 组件，其次看开源 Web 星图库
- 第一轮候选方案控制在 2-3 个以内
- 对象点击后稳定拿到 `name + type` 属于第一阶段最低可接受标准
- 名称体系尽量直连，只做极少量兜底映射
- 第一阶段只接受可轻裁剪的星图方案，不接受重改造方案

这些结论已足以支撑我们继续进入现成星图能力选型、项目结构细化与 API 契约讨论。
